## What was completed today

### 1. Pipeline code fixes

Four files changed in `src/`, one in `app/`, five in `tests/`.

**`src/pipeline.py`**
- Added `load` as the first step of `PRIMARY_STEPS`
- **Why:** `primary_split.py` reads `data/interim/transactions.parquet`, which is produced by `load.py`. `--primary` and `--all` previously failed on a clean checkout with `FileNotFoundError`.
- **Data-driven decision:** no other change. `load.main` was already imported.

**`src/models/train_compare.py`**
- Replaced `TimeSeriesSplit` with month-based expanding-window folds
- **Why:** `TimeSeriesSplit` splits by row position. Because the dataframe is sorted by month, a training fold could contain part of a month and the validation fold could contain the rest of the same month. This violated the documented rule "each fold's validation set is strictly after its training set."
- New fold scheme: fold k trains on months 0..k and validates on month k+1. Five folds on the primary training split (months 0-5).
- Added per-class metrics for the non-fraud class in `evaluate_fold`: `precision_legit`, `recall_legit`, `f1_legit`
- **Why:** the course requires per-class precision, recall, and F1 for **both** classes. Previously only the fraud class was reported.
- Added a **Hyperparameters** table to `reports/model_comparison.md`
- Added a **Selection Justification** section
- Added a **Failure Analysis** section
- **Why:** the course rubric scores the report on documented hyperparameters, tuning procedure, model selection justification, and failure analysis. None of these were in the report before.
- Fixed encoding: `write_text` calls now pass `encoding="utf-8"` for both the report and `cv_results.json`
- **Why:** earlier cp1252 encoding produced a byte `0xb1` for the `+/-` character, which broke UTF-8 reads downstream.

**`src/models/evaluate_compare.py`**
- Added `precision_legit`, `recall_legit`, `f1_legit` to the `metrics` dict
- Added **Selection Justification** and **Failure Analysis** sections to the report
- Kept the idempotent cut at the `## Final Test Results` marker
- **Data-driven decision:** all changes are direct responses to rubric requirements. No refactoring.

**`app/streamlit_app.py`**
- Batch upload: derive `amount_proxy` from `proposed_credit_limit` if missing
- **Why:** if a user uploads raw BAF `Base.csv`, the CSV has `proposed_credit_limit` not `amount_proxy`. Without this, `amt` was `None` and amount scaling was silently disabled inside `route_actions`.
- Manual form: read categorical options from `pre.categories_` with a fallback list
- **Why:** hardcoded options (`AA`, `CA`...) may not match training categories. Unknown values become `NaN` in the LightGBM preprocessor, producing invalid predictions.
- Manual form: pass `proposed_credit_limit` as amount to `route_actions`
- **Why:** `df_row` is built from `features`, which excludes `amount_proxy`. Without this, amount scaling was silently disabled for manual input.

**`tests/`** — see Section 4.

### 6. `requirements.txt` updated for cloud deployment

**Added:**

```
joblib>=1.3,<2.0           # model / preprocessor persistence
streamlit>=1.32,<2.0       # deployed application
```

**Why:** `app/streamlit_app.py` imports both. Streamlit Cloud does not pre-install them. Without these, the app would crash with `ModuleNotFoundError`.

**Removed:** `pyarrow`

**Why:** the deployed app never reads Parquet. It loads `.pkl`, `.json`, and `.yaml`. `pyarrow` is used only by the pipeline locally. Removing it avoids a source build that requires CMake.

**Data-driven decision:** the first Streamlit Cloud build failed with:

```
error: command 'cmake' failed: No such file or directory
ERROR: Failed building wheel for pyarrow
ERROR: Could not build wheels for pyarrow
```

The cause was Python 3.14 in the build container (`cpython-314`). No prebuilt `pyarrow` wheel exists for 3.14, so pip fell back to a source build. The fix was twofold: remove `pyarrow` from `requirements.txt`, and pin Python 3.11 in Streamlit Cloud.

**Python version pinned to 3.11** in Streamlit Cloud Advanced settings.

**Data-driven decision:** tests 1-6 satisfy the course requirement to test with "valid, invalid, and boundary inputs". The widget-level validation (tests 3 and 5) catches out-of-range values before submission. The Python-level `validate_input` catches malformed CSVs (test 6). Both layers verified.
