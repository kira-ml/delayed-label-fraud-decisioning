### Task 2 — `configs/costs.yaml`

**What was done:**
- Wrote the frozen cost matrix:

```yaml
fraud_loss: 1.0
false_positive_cost: 0.1
review_cost: 0.02
residual_fraud_loss: 0.3
```

- Fixed a UTF-8 BOM issue introduced by PowerShell's `Set-Content -Encoding utf8`
  by rewriting the file with Python's `Path.write_text(..., encoding="utf-8")`.

**Why (data-driven justification):**
- These four values are the **frozen cost matrix** from `mvp_architecture.md`
  §5, `decision_policy.md` §6.4, and `evaluation_protocol.md` §4.2.
- They imply two decision thresholds by algebra (not by tuning):
  - `p_review = review_cost / (fraud_loss − residual_fraud_loss) = 0.02 / 0.7 = 0.0286`
  - `p_block  = (false_positive_cost − review_cost) / (false_positive_cost + residual_fraud_loss) = 0.08 / 0.4 = 0.20`
- BOM removal was necessary because a leading `\ufeff` on the first key
  would cause `load_costs()["fraud_loss"]` to raise `KeyError` at
  `decide.py` runtime.

**Verification:**
- `python -c "import yaml; print(yaml.safe_load(open('configs/costs.yaml')))"`
  → `{'fraud_loss': 1.0, 'false_positive_cost': 0.1, 'review_cost': 0.02, 'residual_fraud_loss': 0.3}`

### Task 6 — `src/data/split.py`

**What was done:**
- Filters `observed == True` (drops the 96,843 censored rows).
- Train: `month ∈ {0,1,2}` → `data/processed/train.parquet`.
- Val:   `month ∈ {3,4}`   → `data/processed/val.parquet`.
- Test:  `month ∈ {5,6}`   → `data/processed/test.parquet`.
- Asserts train + val + test = observed total.

**Why (data-driven justification):**
- `evaluation_protocol.md` §3 (Principle 1): "Temporal only. No random
  splits. No shuffling. Ever." A random split would leak future
  information into the training set — for example, a transaction in
  month 0 would be trained alongside a transaction in month 6, giving the
  model access to feature distributions it would never see in production.
- `mvp_architecture.md` §4.3 fixes the split boundaries; changing them is
  documented as a spec change, not a tuning knob.
- The assertion `train + val + test == observed` catches off-by-one month
  overlaps, which would silently leak rows between splits.

**Verification:**

### Task 9 — `src/policy/decide.py`

**What was done:**
- Loads `configs/costs.yaml`.
- For each test row, computes three expected costs:
  - `E[approve] = p × fraud_loss`
  - `E[review]  = review_cost + p × residual_fraud_loss`
  - `E[block]   = (1 − p) × false_positive_cost`
- Chooses `argmin` and writes the action log with all three costs and the
  chosen action.
- Prints derived thresholds as a diagnostic (not used for decisions).
- **Refactored during Task 13:** the argmin logic was extracted into a pure
  function `choose_actions(p, costs)` so it can be called from unit tests
  without file I/O.

**Why (data-driven justification):**
- `decision_policy.md` §5.4 declares the argmin rule as the source of truth.
  Thresholds (0.0286, 0.20) are derived algebraically from the cost matrix —
  not tuned, not searched. This is the core methodological claim of the
  project: thresholds are a consequence of the cost structure.
- The script logs all three expected costs per row (`expected_cost_approve`,
  `expected_cost_review`, `expected_cost_block`). Per `decision_policy.md`
  §10.2, this allows re-scoring under a different cost matrix without
  re-running the model — critical for the amount-scaled sensitivity
  analysis in post-MVP work.
- Labels are deliberately **not** in the action log. They are joined
  in the backtest only. This preserves the log as a pure decision record.
- The refactor into `choose_actions` does not change behavior — verified in
  Task 15 by re-running the full pipeline and confirming identical outputs.

**Verification:**

| Action | Count | Share |
|---|---:|---:|
| approve | 210,734 | 92.64% |
| review | 15,124 | 6.65% |
| block | 1,633 | 0.72% |
| **total** | **227,491** | 100.00% |

- All three actions present, satisfying `mvp_architecture.md` §10 step 6.
- Derived thresholds printed: `p_review=0.0286`, `p_block=0.2000` —
  exactly matching `decision_policy.md` §6.4.

**Artifacts produced:** `data/processed/action_log.parquet`.

### Task 10 — `src/evaluation/backtest.py`

**What was done:**
- Joins action log with test labels on `transaction_id`.
- Computes realized cost for the policy and four baselines under the same
  cost matrix.
- Computes precision@1/5/10% and recall@1/5/10% on the policy's scores.
- Computes Brier score and (informationally) ROC-AUC.
- Reports censored-label counts.
- Writes `reports/mvp_backtest.md`.

**Why (data-driven justification):**
- `evaluation_protocol.md` §2: "Utility is not accuracy. Utility is not AUC.
  Utility is: fraud loss avoided − false-positive cost − review cost."
  The backtest is written to compute exactly that.
- `mvp_architecture.md` §8 defines the four baselines and the per-action
  realized-cost table used here. All five rows use the same split, delay
  regime, and cost matrix — required by `evaluation_protocol.md` §18.
- Censored-count reporting is required by `mvp_architecture.md` §11 and
  `evaluation_protocol.md` §8.4.

**Results (the deliverable table):**

| Baseline | Cost/txn | Total cost | Fraud $ saved vs approve-all |
|---|---:|---:|---:|
| Random | 0.044916 | 10,218.04 | −7,357.04 |

### Task 14 — Unit tests for the policy and the cost matrix

**What was done:**
- Created `tests/test_policy.py` with 7 tests covering the argmin rule and
  the three degenerate cost regimes from `decision_policy.md` §6.5.
- Created `tests/test_backtest.py` with 3 tests covering the realized-cost
  matrix in `backtest.py` and a cross-check between expected and realized
  cost at probability extremes.
- Total: **10 tests, ~1.4 s runtime, no dataset required.**

**Why (data-driven justification):**
- `mvp_architecture.md` §3 says "No `tests/` folder is required for the MVP.
  If you have time on Day 7, add one test for the policy argmin edge cases."
  Day 7 time was available, so the required test was written — and extended
  by one file for the cost matrix, which is the second place a silent bug
  could corrupt the report.
- The tests catch three specific failure modes:
  1. A swapped sign or wrong operation in the argmin (wrong decisions
     across the whole test set).
  2. A degenerate cost matrix (`fraud_loss ≤ residual_fraud_loss`, or
     `p_review ≥ p_block`) silently producing wrong decisions instead of
     raising.
  3. A mismatch between the expected-cost formula in `decide.py` and the
     realized-cost formula in `backtest.py`. These are two separate
     implementations of the same cost table; if they diverge, every number
     in the report is wrong and no other check would notice.

## 11. Honest Observations for the Report

These are noted here so they make it into the presentation and the report's
Limitations section, in line with `mvp_2_weeks.md` §14 ("report honestly").

1. **The static-0.5 baseline barely beats approve-all** (0.012088 vs. 0.012576,
   a 3.9% relative reduction). At a 1.25% base rate, almost no scores cross
   0.5, so the "ML baseline" is nearly equivalent to doing nothing. This is
   the *point* of the project: threshold tuning on imbalanced fraud is a
   failure mode.

2. **Brier score barely beats the trivial baseline.** Predicting the mean
   every time gives Brier ≈ 0.0124. The model gives 0.011881 — a 4.3%
   improvement. This is a property of Brier on highly imbalanced data, not a
   model failure. The meaningful evaluation is realized cost, where the
   policy wins by 26.4%.

3. **Mild distribution drift between train and test.** Train fraud rate is
   ~1.10%; val is 1.0207%; test is 1.2576%. The model is being asked to
   generalize slightly upward between train and test. Documented, not
   corrected — correction would amount to tuning on the test set.

4. **Negative "Fraud $ saved" for Random and Block-all** simply reflects that
   those baselines cost more than approve-all. Worth a one-line gloss in the
   report so the sign isn't misread.

5. **Single delay regime, constant `fraud_loss`.** Both are MVP scope per
   `mvp_architecture.md` §9. Both are candidates for the post-MVP expansion
   in `mvp_2_weeks.md` §15.

6. **The model is not the bottleneck.** Val AUC hit early stopping at
   iteration 55. Further model tuning is unlikely to move the policy
   result; the post-MVP lever is delay regime and cost sensitivity, not
   classifier quality.
