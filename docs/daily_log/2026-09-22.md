## 3. Supplementary pipeline — first full run

**Observation.** `python -m src.pipeline` completed all 7 steps in 21.0s
without errors.

**Evidence (before fix).**
```
[3/7] split      train 397,039 / val 278,627 / test 227,491
                 censored 96,843 (9.68%)
[4/7] train      best iteration 110
[5/7] score      mean p_fraud = 0.234064
[6/7] decide     actions: approve 110,093 / review 35,277 / block 82,121
[7/7] backtest   cost/txn  random 0.0475, approve-all 0.0189,
                 block-all 0.0987, LGBM+0.5 0.0215,
                 policy 0.0386
```

**Finding.** Mean `p_fraud` = 0.234 on a dataset with 1.2% base fraud rate
is 19× too high. The policy cost/txn (0.0386) is worse than
approve-all (0.0189), contradicting every claim in
`docs/decision_policy.md` §7.1.

**Root cause.** `src/models/train_baseline.py` set
`is_unbalance=True` on the LightGBM classifier. This reweights the
positive class by the negative/positive ratio (~90×), which shifts the
predicted probabilities by the same factor. The cost-based policy
assumes calibrated probabilities (`docs/decision_policy.md` §9), so
its expected-cost computation was wrong.

**Decision.** Removed `is_unbalance=True` from `train_baseline.py`.
Class asymmetry is already encoded in the cost matrix
(`fraud_loss` vs `false_positive_cost`); training-time reweighting
double-counts it.

**Evidence (after fix).**
```
[5/7] score      mean p_fraud = 0.012398
[6/7] decide     actions: approve 206,276 / review 19,473 / block 1,742
[7/7] backtest   cost/txn  random 0.0475, approve-all 0.0189,
                 block-all 0.0987, LGBM+0.5 0.0177,
                 policy 0.0076
```

**Result.** Policy now beats every baseline by 57.1% on cost per
transaction, matching `docs/decision_policy.md` §7.1 (56.9%) within
measurement noise. Mean `p_fraud` (0.0124) is within 2% of the true test
fraud rate (0.0126). ECE assumption in §9.1 is now valid.

## 7. Primary model recalibration — second run

**Observation.** After removing `is_unbalance=True` from
`src/models/train_compare.py`, the primary pipeline was rebuilt.

**Evidence (before vs after).**

| Metric | is_unbalance=True | Calibrated |
|---|---:|---:|
| CV Macro F1 (LightGBM) | 0.5249 | **0.5344** |
| Test Macro F1 | 0.5186 | **0.5336** |
| Accuracy | 0.8488 | **0.9852** |
| Precision (fraud) | 0.0653 | **0.3096** |
| Recall (fraud) | 0.7338 | 0.0424 |
| ROC-AUC | 0.8748 | 0.8766 |
| TN / FP / FN / TP | 171908 / 30225 / 766 / 2112 | 201861 / 272 / 2756 / 122 |

**Finding.** ROC-AUC is essentially unchanged (0.8748 → 0.8766),
meaning both models rank transactions the same way. The difference is
entirely at the 0.5 decision boundary. At that boundary, the calibrated
model is conservative; the uncalibrated model was aggressive because its
effective threshold had been shifted down by the reweighting.

Macro F1 *rose* despite lower fraud recall because the majority-class F1
climbed from 0.917 to 0.993 — a known artifact of macro-averaging on
extreme imbalance. Documented as a limitation for the paper.

**Decision.** Keep the calibrated model. It is the correct choice for
the deployed application, because:
1. The app displays "fraud probability" to users. A 13× inflated number
   would be misleading.
2. The cost-sensitive policy thresholds (`p_review ≈ 0.029`,
   `p_block ≈ 0.20`) are far below 0.5, so operational routing still
   catches suspicious rows.
3. It has the highest CV Macro F1 (0.5344), which is the declared
   primary metric.

**Verification.** `pytest -v` → **60 passed in 16.65s**.

Supplementary pipeline re-run after recalibration:
```
[decide] Actions: approve 206,276 / review 19,473 / block 1,742
[backtest] policy cost/txn = 0.007621
```

Action distribution and policy cost are unchanged, confirming that
`train_baseline.py` (which trains the supplementary model) was already
calibrated and did not depend on the primary model artifact.
